# Notification acceptance and completion gates

The default E2E suite never delivers to real recipients. The new
`test_notification_workflows.py` closes the gap between a real user action and
the outbound provider request; it does not certify live delivery.

## What the new tests execute

There are 31 cases. None manually inserts an outbox notification. They use the
real request APIs, booking/status logic, PostgreSQL queue, notification router,
Twilio wrapper, and installed Twilio SDK. Only the SDK's final HTTP transport
is captured; external calendar projection is stubbed independently.

The capture installs fake credentials, then removes `TESTING` and
`PYTEST_CURRENT_TEST` during the test call so Twilio's automatic mock-success
branch cannot satisfy these assertions. Network guards remain enabled. Requests
must be POSTs to the Twilio Messages resource; responses contain synthetic SIDs.
Callback requests use real signature verification and durable replay protection.

| Journey | Assertions |
| --- | --- |
| Booking; reschedule; customer/admin cancellation; in-progress/completed status | Transaction-generated event, persisted processing outcome, exact recipient set, selected SMS/WhatsApp channel and sender, relevant body/confirmation prompt, stored SID/body, signed delivery callback, callback replay, no resend after completion |
| Reassignment | Customer/admin/new/previous staff recipients and selected channel; immediate API processing is permitted but durable event ownership is required |
| Flat/wrapped voice booking | Real tool-created booking produces a customer request using E.164 identity; callback updates the actual dispatch |
| Opt-out, disabled matrix, test whitelist | No provider call and appropriate skipped/no-dispatch state |
| Transient failure and exhausted retries | Failure persisted, no early retry, identical target/body/channel on retry, terminal failure stops work without undoing the committed booking |
| Partial failure | Retry the failed recipient without resending a successful recipient |
| Worker concurrency and stale claims | One delivery for concurrent workers; expired claim can recover |
| Booking-generated reminders and staff confirmation | Generated reminders reach the SDK once; signed confirmation cancels remaining staff prompts |
| Quiet hours | A real booking queues a dispatch; release preserves its body/channel/log identity and runs once |
| Provider callbacks | Invalid signatures cannot change logs; actual SID's delivered/failed outcome and error details persist; duplicates have no extra effect; a late `sent` event cannot downgrade delivery |

Most dispatch-contract tests explicitly drain real single-event worker batches
to isolate failure causes. A separate test calls the normal cron endpoint and
requires it to handle **both events generated by a booking in one batch**. The
single-event runs are not a substitute for this production-batch requirement.
Reminder/quiet-release due times are advanced only for rows generated by the
real booking workflow; no reminder or notification event is fabricated.

## Confirmed implementation defects

On 2026-10-07, the focused notification run produced **27 passed, 4 failed**.
The complete expanded suite produced **124 passed, 4 failed** across 128 cases;
the same four failures occurred in both runs. Report: `scratch/e2e-review.xml`.
These are ordinary failing acceptance tests, not xfails or skips. No application
implementation was changed in this coverage extension.

1. **Normal multi-event batches crash.**
   `test_cron_processes_all_events_generated_by_real_booking` receives HTTP 500.
   A diagnostic identifies `cursor already closed` in `process_outbox_batch`:
   its inner success-update context shadows and closes the outer selection/
   claim cursor, which the next iteration then tries to use. Keep cursor
   lifetimes independent and verify claiming/retry behavior across the whole
   batch, including concurrency. Source: `serviceBot/services/outbox_worker.py`.
2. **Reassignment ignores staff's selected WhatsApp channel.**
   The `REASSIGNED-WHATSAPP` lifecycle case captures SMS requests for new and
   previous staff while customer/admin requests correctly use WhatsApp.
   `reassign_service_request` sends direct `send_sms` calls outside the matrix
   router. Route all recipients through the same durable, channel-aware owner.
   Source: `serviceBot/api/portal.py`.
3. **Partial failure duplicates successful delivery.**
   `test_partial_failure_does_not_resend_successful_recipient` captures a second
   customer message when only the staff delivery failed. The worker retries
   the whole event, and the router does not suppress completed per-recipient
   dispatches. Persist per-event/recipient/channel progress and retry only
   incomplete work. This is distinct from preventing two worker claims.
   Sources: `serviceBot/services/outbox_worker.py`, `sms_router.py`.
4. **Out-of-order callbacks regress delivery status.**
   `test_delayed_sent_callback_does_not_regress_delivered_notification` observes
   `DELIVERED` become `SENT`. Replay protection only rejects an identical event;
   a distinct, older lifecycle status is still applied unconditionally. Enforce
   monotonic transitions for a given provider SID. Source:
   `serviceBot/api/telephony.py::sms_status_callback_webhook`.

## Definition of done

- [x] Start tests from real booking/voice/lifecycle actions, not synthetic queue events.
- [x] Verify the actual SDK request and callback read-back, not mock `SENT` alone.
- [x] Exercise suppression, retries, concurrency, reminders, and quiet release.
- [ ] Fix the four failing implementation requirements and rerun the full suite.
- [ ] Cover ambiguous provider timeouts, crash after provider acceptance, retry
  identity, cross-channel partial failures, opt-out after quiet-hour queueing,
  all reminder horizons/late-confirmation races, and supervisor escalation.
- [ ] Separately validate production worker startup, ownership, shutdown, and
  restart behavior; these tests explicitly invoke cycles under pytest.
- [ ] Run a controlled live provider journey using approved sandbox recipients
  and verify both provider evidence and the application's callback/read-back.

The wider application still has the gaps listed in [COVERAGE.md](COVERAGE.md):
voice conversations/LLM behavior, retrieval, OAuth success, email delivery,
security/access, performance, and more. This extension is not a whole-app parity
claim.

## Safe live-delivery gate

Live delivery must be a **separate opt-in workflow**, never a switch that turns
all synthetic tests into real sends. Before implementing/running that workflow,
agree on:

1. A dedicated sandbox/test deployment and provider account/sender, an exact
   approved recipient list, selected SMS/WhatsApp channels, and a maximum send
   count. No production customers, staff, or broad matrix recipients.
2. Credentials supplied through approved runtime configuration, not committed
   fixtures or captured request artifacts. Do not print authorization headers.
3. Provider-valid recipients/WhatsApp onboarding, and a publicly reachable,
   signature-verified callback URL for that deployment.
4. One bounded booking journey with an explicit worker trigger and timeout.
   Read back the provider SID/status and the matching application dispatch.
   `SENT`/API acceptance alone is not handset receipt; verify a delivered/read
   callback and, when required, the approved recipient's receipt.
5. Cleanup only test-owned records, retain a redacted report, and report blocked
   dependencies as blocked—not successful or silently skipped.

The application's current Twilio guard treats the **presence** of `TESTING` or
`PYTEST_CURRENT_TEST` as mock mode, so setting `TESTING=0` is not a live-send
switch. A live harness needs deliberate separation from the normal test
process, not accidental removal of safety guards from `e2e/conftest.py`.
